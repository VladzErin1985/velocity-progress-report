July 7: I continued the ongoing workflow-by-workflow audit into Konsier’s Stripe payment handler — the workflow that fires when a customer completes checkout, moves their deal to the Won/Onboarding stage, and kicks off the rest of the onboarding chain. I found a real bug in the fallback path this workflow uses when a payment doesn’t carry a direct link back to the original deal: that fallback searches for the customer’s open deal by looking in the pipeline the deal only reaches after this same workflow moves it there — meaning the one path built specifically to handle a missing deal reference could never actually find one. I fixed the search to look in the two pipelines a deal is genuinely open in before payment instead. I also found the Pipedrive key hardcoded in plain text in three more places in this workflow and moved all three into proper credential storage, continuing the same cleanup from July 6. Two smaller correctness fixes alongside that: the onboarding page link was missing its display name, and three lookup expressions were written with a shorthand syntax this platform doesn’t reliably support — I rewrote all three with an equivalent form that resolves safely either way. Separately, I added a signature-check step to this workflow’s listening endpoint, switched off for now. This endpoint deliberately doesn’t use the platform’s dedicated Stripe listener — that one was replaced back on June 5 after its automatic security-key handling kept silently desyncing after routine edits, rejecting real payment events with no visible error anywhere. The fixed listening endpoint built to replace it is reliable but doesn’t check who’s actually sending it data, so I built the verification step as a self-contained check that doesn’t touch the listener itself, ready to switch on the moment I confirm the current signing key for this specific endpoint. Two things are flagged rather than changed today: whether a compliance gate for HIPAA-related fields that appear to have been built specifically for this workflow actually needs to exist here — there’s currently no trace of one in the live workflow, worth a quick confirm before assuming it’s fine; and this workflow has no safeguard yet against the same payment event being delivered twice, which happens routinely on any payment platform — a repeat delivery right now would create a second duplicate onboarding record and a second duplicate alert instead of recognizing it as already handled. Later the same day I continued the same node-by-node audit pass onto two more Velocity Capital handoff workflows — the ones that automatically create a new investor deal when a policy client’s coverage is delivered, and a new acquisition deal when an investor commits capital. Both were already correct on every stage ID and field I checked, a cleaner starting point than some of the earlier finds. I found the same hardcoded Pipedrive key sitting in every request across both workflows and moved it into proper credential storage, the same fix I’ve been applying everywhere else. I also found something neither workflow had ever been checked for: if the same handoff event ever gets delivered twice — which happens on any webhook system, not something unique to this setup — both would have silently created a second duplicate deal for the same person with no warning. I added a check to both: before creating the new deal, look up whether one already exists for that person, and if it does, skip the creation and post a Slack notice explaining why instead of duplicating the record. Later the same day I built the next item on the Velocity Capital V3 list: WF-08 Project Milestones + Cost-Seg ✓ (24 nodes, inactive placeholder). This one mirrors construction milestones onto the project’s deal stage as they happen, and when a project reaches its final inspection milestone, it automatically opens a cost-segregation review task, has the reporting agent draft a first-pass cost-seg packet for the CPA and attorney to review, and creates the follow-on property-management record so the completed property moves into ongoing management without anyone re-entering it by hand. The draft packet is explicitly marked for professional review and never gets sent anywhere on its own — it lands as a pinned note and a Slack alert, same as everything else on this project that needs a human sign-off before going out. This one stays inactive until the milestone-tracking connection is actually wired up on the construction-management side, and I’d like a quick confirmation on which stage a completed property should land in once it moves into property management, since I made a reasonable assumption there rather than guessing at something more consequential. Technical Discoveries (June 2026)

[June 23] Pipedrive enum custom fields require integer option IDs — not label strings. Each enum option has a numeric id value and a display label. Passing the label string when writing to a Pipedrive enum field silently fails — Pipedrive accepts the write without setting the value. Always look up the integer option ID from the field configuration and hardcode it into the workflow.
[June 23] n8n IF node (v2.2) unary operators (“true”, “false”, “empty”, “notEmpty”) require "singleValue": true inside the operator object — the n8n workflow validator will reject the node otherwise. Binary operators (equals, contains, greaterThan) must NOT include singleValue. Also: the conditions object requires "options": {"version": 2} alongside the conditions array — omitting it causes a validation error.
[June 23] n8n Webhook node with responseMode: “responseNode” requires a LINEAR chain (Webhook → Respond to Webhook → processing nodes). Connecting Webhook output to both Respond to Webhook AND a processing node in parallel triggers a validator error. The correct pattern: Respond to Webhook fires immediately (200 OK to caller), then n8n continues executing the downstream chain asynchronously. Also requires onError: “continueRegularOutput” on the Webhook node. When rewiring workflow connections, replacing the entire connections map is more reliable than removing and re-adding individual connections — especially for node names containing special characters.
[June 23] SAM.gov API v2 (api.sam.gov/opportunities/v2/search) returns results under opportunitiesData array (not data). Place-of-performance state is at placeOfPerformance.state.code. Agency hierarchy is in fullParentPathName as a dot-separated string (e.g. “DEPT OF DEFENSE.DEPT OF ARMY.CORPS”). Primary contracting officer is in pointOfContact array where type === 'primary'. Response deadline is in responseDeadLine ISO format — trim to first 10 chars for Pipedrive date field.
[June 23] n8n Code node validator flags “Cannot return primitive values directly” when a filter() callback inside runOnceForAllItems mode uses explicit return true / return false statements — the validator scans returns statically and misidentifies callback returns as top-level returns. Fix: replace filter + explicit-return dedup with a Map-based loop (dedupMap.set(key, value)) which avoids bare return statements.
[June 22] Pipedrive custom field type: “integer” is not a valid field type for deal fields or person fields — Pipedrive returns a validation error even though the UI can display whole numbers. Use “double” for any numeric field (whole or decimal). Pipedrive renders double fields as clean integers in the UI regardless.
[June 22] Pipedrive stage rename preserves the stage ID — only the display name changes. All downstream n8n workflow conditions, routing logic, and Pipedrive native automation triggers that reference a stage ID by number remain fully valid after a rename. Stage IDs only change if you delete and recreate the stage, so renames are always safe without touching any workflow logic.
[June 22] Pipedrive Deal Link custom field (28acc196575fb788fca703799c49a6280920bb38) is a shared field across all 4 entity pipelines (VC, AV, AR, AC) — the same field key reads and writes on any pipeline’s deal. No per-pipeline lookup required. Use it in any cross-entity workflow step to set a back-reference URL from the new deal to the originating deal.
[June 24] Pipedrive notes API — pinned_to_deal_flag: 1 in the POST /v1/notes body pins the note to the deal record for immediate visibility when opening the deal in Pipedrive. Without this flag, the note is written to the activity feed only and does not surface prominently in the deal view — critical for workflow-generated drafts that require immediate review before action.
[June 25] USAspending.gov (/api/v2/search/spending_by_award/) filters on action_date (obligation/modification date) by default — not period-of-performance end date. To target contracts expiring in a future window, use a broad 5-year past action_date range to capture all active multi-year contracts, then apply client-side POP end date filtering in a Code node. USAspending is fully free and keyless — POST with JSON body only. NAICS filtering via naics_codes array in the filters object. Award type codes A, B, C, D = definitive contracts (excludes IDIQs, delivery orders, grants). Response fields include Award ID (PIID), Recipient Name, Awarding Agency, End Date, Award Amount, and Place of Performance State Code.
[June 26] n8n Slack node (typeVersion 2.2) requires channelId as a resource-locator object — { __rl: true, value: “C086BRLVBUP”, mode: “list”, cachedResultName: “all-velocity-capital” } — not a plain channel string parameter. Setting channel: “#all-velocity-capital” causes an activation error. Additionally, the correct credential type is slackApi (not slackOAuth2Api); adding authentication: “oAuth2” in parameters forces the wrong credential lookup. Always model new Slack nodes directly from a confirmed-working workflow (WF-14) rather than relying on validator defaults alone.
[June 26] n8n Code node mode mismatch: .first() is only available in “Run Once for All Items” mode — calling $input.first() or $('Node').first() inside a Code node set to “Run Once for Each Item” throws “Can't use .first() here” at runtime. The validator does not catch this at build time. Always set Code nodes that reference .first() to runOnceForAllItems. In a single-item webhook context the two modes behave identically — the only difference is which helper methods are available.
[June 26] n8n typeVersion mismatch between validator recommendations and the n8n instance version (2.59.0): general upgrade guidance suggests IF nodes at typeVersion 2.3 and Slack nodes at typeVersion 2.5, but these versions do not exist in n8n 2.59.0 — activating a workflow with these typeVersions throws “Cannot read properties of undefined (reading 'execute')” with no further detail. Always match typeVersions against a confirmed-working active workflow on the same instance (WF-03 Bid/No-Bid is the reference): IF = 2.2, Slack = 2.2, Webhook = 2, Respond to Webhook = 1.1. Also: Slack node at typeVersion 2.2 requires credential type slackOAuth2Api (not slackApi) with authentication: “oAuth2” parameter.
[June 24] n8n chained webhook workflows (WF-01 → WF-03 → WF-04): each workflow is independent and communicates via internal HTTP POST to http://localhost:5678/webhook/[path]. The calling workflow adds onError: continueRegularOutput on the trigger node so it never fails if the downstream workflow is unreachable. The called workflow uses responseMode: responseNode + Respond to Webhook (200 OK) to release the caller immediately and continue asynchronously. Pass all needed context in the POST body — downstream nodes cannot reference the calling workflow’s node data.
[June 29] n8n expression space bug: "= {{ $json.field }}" (space after the equals sign) causes n8n to treat the value as a string template rather than a computed expression, producing " 0" (string with leading space) instead of 0 (number). Strict-typed APIs like Notion reject this silently — the error says “should be a number, instead was string” but the root cause is an invisible space character in the field editor. Always write expressions as "={{ $json.field }}" with no space between = and {{.
[June 29] Claude output schema discipline: specifying “Strict JSON only. No markdown.” in a system prompt is insufficient if you don’t also define the exact key names. Claude will return valid JSON but with arbitrary key names of its own choosing (e.g. title instead of brief_title). Downstream nodes referencing $json.brief_title receive undefined with no error at the Claude node. Always include a complete example JSON object with exact key names and value types in the system prompt whenever a Claude node feeds structured data to downstream workflow nodes.
[June 30] n8n patchNodeField uses dot-notation to target elements inside a nested array — parameters.assignments.assignments.6.value to reach index 6 of a Set node’s assignments array. Bracket notation ([6]) returns “property does not exist” even for valid array positions. Use dot-path notation throughout when targeting any element inside an assignment array, connection spec, or nested object field in n8n workflow JSON.
[June 30] n8n connection operations use source and target parameters (not from/to). For node names containing em-dashes (—), the name lookup fails in connection operations — use node IDs as source/target values when the node name contains special characters. IF node branches specify branch: “true”/“false” and Switch cases use case: N as smart parameters on the connection call.
[July 1] A voice agent’s spoken introduction and its scripted opening line live in two separate places — updating the instructions the agent follows does not automatically update the exact first sentence it speaks on a call. Both the internal script and the standalone opening-line field have to be updated together, or the agent will still greet callers with its old name.
[July 2] n8n’s per-node “continue on fail” setting is deprecated in its old boolean form in favor of a newer error-mode property with named options (continue with regular output, continue down a dedicated error path, or stop the workflow). Functionally similar for the simple case, but the newer form gives finer control and shows up correctly in the n8n UI — worth using on any new node going forward instead of the old boolean flag.
[July 2] Pipedrive’s deal “rotting” status is a real field on the deal record (a timestamp, not just a UI color), set automatically once a deal has gone past the inactivity window configured on its pipeline stage with no activity logged. Reading that field directly in code is far more reliable for a re-engagement workflow than trying to compute staleness manually from last-activity dates.
[July 6] The validator on this n8n instance produces a consistent false-positive pattern on three specific checks: Slack “post message” nodes with no explicit operation field flagged as invalid, Code nodes returning arrays through a .map() chain flagged as “cannot return primitive values,” and expressions using JavaScript template literals inside a .map() callback flagged as invalid syntax — all three are confirmed working correctly against real execution history across multiple workflows. Always check actual execution logs before treating these three warning types as real bugs on this instance.
[July 6] A workflow that has never actually run has no execution history to lean on — the same warnings proven harmless elsewhere by checking real run logs can’t be assumed safe on a workflow that has only ever existed as a paused placeholder. The right fix is a one-time test run with sample data before activation, not carrying over an assumption from a similar-looking workflow.
[July 6] A workflow can pass every build check with zero errors and still silently do nothing — found a save step that had an empty request body since the day it was built, ran clean every single time, and simply wrote no data anywhere. A clean validation result confirms structure, not that the data actually being written is correct or even present — worth an occasional line-by-line read of exactly what a step is sending, not just a passing check.
[July 7] A fallback lookup path can be perfectly valid, error-free syntax and still be dead code — found a backup search step filtering for records in a pipeline that a deal only reaches after the very same workflow moves it there, so the filter could never match anything. No validator catches this kind of thing; it only surfaces from actually reading the business logic line by line, not from a clean build check.
[July 7] A payment platform’s own dedicated listener node isn’t automatically the safer choice — its automatic security-key management can silently break after routine edits, rejecting real events with zero visible error. A manually built listener with its own explicit verification step is more setup up front but fails loudly instead of silently, which matters more for anything handling real payments.
[July 7] Any handoff step that creates a new record in response to an event should check whether that record already exists first — the same event can arrive more than once on any webhook-driven system, and without a duplicate check, a repeat delivery silently creates a second copy of the same deal instead of being recognized as already handled. Worth building this check in from the start on every new handoff workflow, not just adding it after finding the gap.
