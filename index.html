VELOCITY CAPITAL — MONTHLY INVESTOR UPDATE AUDIT (PD-WF-09, 10→13 nodes) + WF-10 WEBINAR → INVESTOR BUILD, BRANCH 1 (17 nodes): I audited the workflow that runs on the first of every month, pulls every active investment deal in the portfolio, and has the reporting agent draft an internal summary posted to the team channel for Drew — it came back mostly clean, with the pipeline stage it filters on, all four of the financial fields it pulls (investment amount, funded amount, soft commit, target IRR), and the AI model configuration all confirmed correct directly against the current reference tables. I fixed the last hardcoded access key on it, moved into secure credential storage, added retry protection to both of its outbound steps, and added a safeguard it had no version of at all: since it runs on a monthly schedule with nothing checking whether it already ran this month, a restart or accidental manual re-run before the month changed would have quietly re-posted a duplicate investor update to the team channel — it now checks first and skips a duplicate run instead. Separately, I started building the workflow that turns a webinar registration into a tracked investor prospect — this is a bigger build than most, with four distinct pieces planned, so I'm building and testing it one piece at a time rather than all at once. Today's piece was the foundation: the core event-handling flow everything else will build on top of. When a webinar registration or attendance event comes in, it first checks whether that person already exists as an investor prospect — if they do, it finds their existing record; if not, it creates a brand-new one — so the same person registering for a second webinar doesn't end up with two separate records. Either way, they land in the Webinar/Deck stage, and the workflow then branches on how long they actually stayed on the call: over 25 minutes logs that a deck and a follow-up conversation are owed, anything shorter logs a lighter note instead. The two steps that create a brand-new record are the ones that matter most if something goes wrong there, so instead of just a simple retry I gave those a stronger safeguard: a genuine failure now posts directly to the team channel so it gets caught by a person, rather than the lead silently falling through. I documented two things directly in the workflow itself rather than quietly assuming them: the exact shape of the webinar tool's event data isn't confirmed yet, so today's build works off a reasonable assumption that'll need a quick check once we're connected to the real tool; and the actual sending of the deck email isn't wired up yet either, since no email tool has been confirmed for that specific send — it logs the obligation as a task instead of pretending to send something it can't. Three pieces remain before this workflow is complete: the part that answers a lead's follow-up questions (which will run through the same compliance review every other AI-drafted message here goes through before anything sends), the part that sends the actual investor-verification link once someone shows real interest, and the part that marks someone verified once that verification comes back. KONSIER — LINKEDIN REPLY HANDLER AUDIT (KS-WF5, 11 nodes): I audited the workflow that handles every LinkedIn connection acceptance and message reply from our outreach campaigns and routes each into the CRM, and found the most serious problem uncovered in any audit so far. An extra invisible character — the same kind of formatting mistake found in smaller doses elsewhere this week — had been copied into fifteen separate places across three different steps in this one workflow, including the step that decides which of the two event types just arrived. Tracing exactly what that mistake does confirmed something worse than a garbled label: the corrupted value gets read a second time by the very step deciding what kind of event just came in, compounding the mistake, so that step could never correctly recognize either a new connection or a reply, no matter what actually arrived. Since there was no fallback path built for an unrecognized event, every single LinkedIn event this live workflow has received since the day it went live has been silently discarded, with nothing anywhere to show anyone that anything had gone wrong. Fixed all fifteen instances and confirmed, through a second full check of the corrected workflow, that the decision step now correctly recognizes both event types for the first time. Also moved the last hardcoded access key across all five outbound steps into secure credential storage and added retry protection to each. Two more gaps are flagged for a follow-up rather than built today: neither the reply-handling path nor the new-connection path has any protection yet against, respectively, a reply from someone not yet in the CRM, or the same connection event being delivered twice. VELOCITY CAPITAL — PROJECT MILESTONES + COST-SEG AUDIT (WF-08, 24 nodes): I audited the workflow that mirrors construction-project milestones onto the deal stage and, once a project hits its final inspection milestone, automatically opens a cost-segregation review task and has the reporting agent draft a first-pass cost-seg packet for the CPA and attorney to review. This one came back genuinely clean rather than turning up a new problem. I checked all nine of its hardcoded milestone-to-stage mappings directly against the current pipeline stage table and every single one is correct. Both of its decision branches are fully wired on each possible outcome, and the safeguard against a repeated delivery creating a second duplicate onboarding record was already correctly built in and placed on exactly the step that needed it. The only real gap was the same one found on most workflows this week: none of its nine outbound steps, including the AI-drafted cost-seg packet itself, had any protection against a single failed or slow response silently halting the rest of the chain partway through. Added that protection to all nine, plus the standard missing webhook safeguard. KONSIER — CLOSED-WON TO ONBOARDING HANDOFF AUDIT (KS-WF4B, 9 nodes): I audited the workflow that fires the moment a deal closes — pulling the client’s information from the CRM and kicking off their onboarding draft, including a compliance gate that holds onboarding if a client’s industry requires a signed data-protection agreement that isn’t in place yet. I found two real problems that had never surfaced before, since this workflow has never actually fired on a real deal. The first: the industry value passed along to the onboarding draft was being sent twice under the same label, with the second, broken copy silently overwriting the correct one with nothing at all — meaning every onboarding draft generated through this path would have used generic default guidance instead of the industry-specific compliance rules and messaging that industry actually needs. The second, more subtle: seven of the nine pieces of information sent along with that handoff — business name, owner name, industry, plan tier, and more — had an extra invisible character baked into how each one was written, which would have silently prefixed every one of those values with a stray equals sign on arrival, so a business name would have shown up as “=Acme HVAC” instead of “Acme HVAC” in the client’s actual onboarding record. Fixed both. The compliance gate itself — checking whether a client’s industry requires a signed data-protection agreement, and holding onboarding with a direct alert if one isn’t in place — was already correctly built, with both possible outcomes properly wired, so nothing needed fixing there. Also moved the last hardcoded access key in this workflow into secure credential storage and added basic retry protection to its three outbound steps. KONSIER — CALENDLY BOOKING WORKFLOW AUDIT, ALL FOUR BRANCHES (KS-WF-CAL, 29→44 nodes): I audited the workflow that handles every stage of a client’s calendar relationship with us after they book — the initial demo, the kickoff call, a mid-engagement check-in, and the 30-day review — and found the largest single exposure of an access key anywhere in this codebase: the same key was hardcoded across nine separate outbound steps, spanning all four branches. Migrated every one into secure credential storage. I found a more serious problem while tracing the wiring on the three non-demo branches: the outcome for “we couldn’t find this client’s account” wasn’t connected to anything at all on any of the three — a kickoff, check-in, or 30-day-review event for a client whose account couldn’t be matched would simply vanish, no alert, no record, nothing. I wired all three to a dedicated alert instead. I also added the same duplicate-delivery protection now standard across this codebase to all three branches, so a repeated calendar event can no longer log the same note or ping the team twice. I tested the fixed workflow against a real trigger afterward and confirmed it working end to end — it correctly recognized that one specific scenario had already been logged once before and skipped creating a second copy, posting its own distinct notice instead, proof the new safeguard does exactly what it was built to do rather than just looking correct on paper. Added the missing safeguard on the entry point, matching every other workflow fixed this way. I also added the same duplicate-delivery protection used elsewhere, specific enough that completing two genuinely different course modules still both get recorded rather than the second one being mistaken for a repeat. Confirmed the workflow completes cleanly end to end for the first time since it was built. Technical Discoveries (July 2026)

[July 16] A fix already confirmed working once can quietly come undone later with no record of when or why — worth checking a workflow's current state against your own past notes on it before assuming an old fix still holds, especially on one that's been edited many times since. The exact same corruption pattern already fixed once on this workflow's main AI step had reappeared on a different step nearby that was never touched by that original fix.
[July 16] A step that flags when an AI's response failed to come back as valid, usable data is only useful if something downstream actually reads that flag — found a workflow generating the right signal on a bad response every time, with nothing after it ever checking, so a failure would still file a blank draft and report success. Separately: a specific field the AI is asked to generate can come back correct every single run and still never reach anywhere a human sees it, if nothing downstream ever explicitly reads that one field by name.
[July 16] Checking a workflow's stage and field logic against the current specification and confirming it's already correct is just as valuable an audit outcome as finding a bug — worth explicitly checking and recording every time, not just when something looks off, since a similar-looking workflow audited earlier the same week turned out to have exactly this kind of mismatch.
[July 16] A compliance review step proven working on one outbound AI-drafted message doesn't automatically cover every other workflow that sends AI-drafted content to a real person — nothing shares that protection across workflows structurally, so each one needs the same gate wired in individually, and it's worth checking every AI-to-real-person send point by name rather than assuming a proven pattern elsewhere already applies.
[July 17] A downstream workflow's own safety gate can be silently defeated by an upstream step reporting a hardcoded, unconditional outcome instead of the real computed one — the gate itself was working exactly as designed, it was just never receiving an honest input to check. Worth tracing what value actually gets sent into any safety check, not just confirming the check exists and looks correct in isolation.
[July 17] Reconciling a self-authored process document against an official, later-arriving version of the same document is worth doing explicitly rather than assuming either one alone is complete — the official version had real, usable additions (escalation chain, pricing, compliance rules) worth merging in, while also referencing at least one system that was never actually built. Worth checking every reference in an official document against what's actually live before training anyone against it.
[July 17] A report or query that filters on a record's "open" status can quietly stop finding anything the moment that record gets marked complete/won elsewhere — especially risky when the very stage name it's filtering for describes the end of the process. Worth confirming directly how a stage is actually managed day to day before assuming a status filter still covers it, rather than either assuming it's fine or guessing at a fix.
[July 20] A branch reporting no match found isn't automatically safe just because the matched-record branch works correctly right next to it — found three separate outcomes all sharing the exact same gap: nothing wired to the "not found" case at all, so that specific event type would vanish completely with zero trace every time it happened. Worth checking every branch of a multi-outcome step individually rather than assuming coverage because a sibling branch looks complete.
[July 20] Adding a new safety check in front of an existing step can silently break a reference that step was quietly relying on, even when the new check and the old reference have nothing to do with each other on the surface — both a web address and a data value pointed at "whatever ran right before me" instead of the real original source, and once a new step sat in between, both went silently blank. The fix held for one before being caught for the other on the same step, a reminder to check every reference on a step being repositioned, not just the first one found.
[July 20] A workflow deliberately left half-finished isn't automatically the same thing as a workflow that's fallen behind — checking a build against its original specification first, before assuming anything needs fixing, showed the open questions from months ago were still genuinely open, and the parts left unbuilt were exactly the parts honestly documented as waiting on those answers. Worth confirming a build's gaps are still real open questions rather than just assuming either "it's outdated" or "it's fine" without checking.
[July 21] An extra invisible character in front of a value's formatting can compound if the same corrupted value gets read a second time by another step written the same way — found in the exact step deciding what kind of event just arrived, meaning that step could never correctly recognize any event at all, no matter what came in. Since there was no fallback for an unrecognized event, this meant a live, active workflow had silently done nothing with every real event it received since going live, with zero errors anywhere. Worth scanning an entire workflow for this exact formatting pattern the moment it's found once, not just the field where it was first spotted, since it tends to get copied across several steps built the same way.
[July 21] Confirming a workflow is genuinely clean is just as valuable an audit outcome as finding a bug in it — systematically checking every hardcoded stage mapping directly against the current pipeline table, tracing both outcomes of every decision branch, and confirming a duplicate-delivery safeguard was already correctly placed on exactly the step that needed it turned up nothing wrong, which is itself real, worth-recording confidence rather than an audit with nothing to show for it.
[July 21] When the same piece of information gets sent twice under the same label as part of a handoff, whichever copy is written last silently wins — and if that last copy references something that was never actually built, the correct value from earlier gets overwritten with nothing at all. Worth checking a handoff step's full list of fields for accidental duplicate labels, not just confirming each individual field looks correctly written.
[July 21] An extra, invisible leading character on a value's own formatting — separate from the value itself — can silently prefix every result with a stray symbol on arrival, with nothing about it looking wrong in a structural read. Confirmed on seven of nine fields in one handoff step, all copy-pasted from the same original mistake. Worth checking a field's exact formatting character by character when several fields in the same step were clearly built by copying one working example, since a mistake in the original copies forward every time.
[July 22] A duplicate-run safeguard doesn't have to check an external record every time — when a report has no single business record to attach a marker to, the workflow's own persistent memory can hold that same "have I already done this" check directly, with nowhere else needed to look. Worth reaching for this lighter option whenever the usual attach-a-marker-to-a-record pattern doesn't have an obvious record to attach to.
[July 22] A summary dashboard that only ever gets new rows appended to it can quietly drift from reality on the sections nobody's re-checking — one workflow still showed as "Queued" two weeks after it was actually built, audited, and confirmed clean, and a second finished workflow had no card here at all. Worth periodically re-validating summary/status sections against the actual current build state, not just adding today's update on top and assuming everything below it is still accurate.
