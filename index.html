KONSIER — CALENDLY BOOKING WORKFLOW AUDIT, ALL FOUR BRANCHES (KS-WF-CAL, 29→44 nodes): I audited the workflow that handles every stage of a client’s calendar relationship with us after they book — the initial demo, the kickoff call, a mid-engagement check-in, and the 30-day review — and found the largest single exposure of an access key anywhere in this codebase: the same key was hardcoded across nine separate outbound steps, spanning all four branches. Migrated every one into secure credential storage. I found a more serious problem while tracing the wiring on the three non-demo branches: the outcome for “we couldn’t find this client’s account” wasn’t connected to anything at all on any of the three — a kickoff, check-in, or 30-day-review event for a client whose account couldn’t be matched would simply vanish, no alert, no record, nothing. I wired all three to a dedicated alert instead. I also added the same duplicate-delivery protection now standard across this codebase to all three branches, so a repeated calendar event can no longer log the same note or ping the team twice. I tested the fixed workflow against a real trigger afterward and confirmed it working end to end — it correctly recognized that one specific scenario had already been logged once before and skipped creating a second copy, posting its own distinct notice instead, proof the new safeguard does exactly what it was built to do rather than just looking correct on paper. VELOCITY CAPITAL — EDUCATION PROGRESS TRACKING AUDIT, RE-APPLIED + ENHANCED (PD-WF-08): This workflow records a client’s progress through the education curriculum back onto their CRM record. The findings from an earlier pass had been reverted rather than applied, so I redid the work today: migrated the last hardcoded access key, and separately found this workflow was using a different, less consistent method of authenticating than every comparable step elsewhere in this codebase — corrected it to match the proven pattern. Added the missing safeguard on the entry point, matching every other workflow fixed this way. I also added the same duplicate-delivery protection used elsewhere, specific enough that completing two genuinely different course modules still both get recorded rather than the second one being mistaken for a repeat. This workflow had never actually processed a real event before today, and testing it for real surfaced two genuine problems a clean-looking build would never have caught: the step checking for a valid record reference was rejecting a perfectly real value because of an overly strict comparison rule, inconsistent with how every other similar check in this codebase is built — corrected to match. Separately, adding the new duplicate-check step in front of the existing write step silently broke two references that had been quietly relying on the step immediately before them, without anyone building today realizing either one depended on that specific position in the chain — both now point at the original source data explicitly instead. Confirmed the workflow completes cleanly end to end for the first time since it was built. VELOCITY CAPITAL — OWNER OUTREACH WORKFLOW, SPEC-COMPLIANCE AUDIT (WF-07): I checked this workflow — the one that drafts and sends compliance-reviewed outreach to property owners as part of the deal-sourcing pipeline — against the original specification before touching anything, since real design questions were still open the last time this was looked at. Confirmed nothing has changed: the same open questions from that original document remain unanswered, and no newer direction has come through since. The workflow itself is honestly built around that reality already — the AI-drafted outreach copy and the compliance-review gate in front of it are both real and correctly wired, while physical-mail delivery, the sending domain, and text messaging are deliberately left as clearly-marked placeholders until those questions are answered, exactly as they should be. Nothing on the design side needed fixing. What I did fix: the last hardcoded access key in this workflow, tucked into a spot easy to miss compared to where it usually shows up in similar workflows, plus the same missing webhook safeguard found on nearly everything else this week. [June 23] Pipedrive enum custom fields require integer option IDs — not label strings. Each enum option has a numeric id value and a display label. Passing the label string when writing to a Pipedrive enum field silently fails — Pipedrive accepts the write without setting the value. Always look up the integer option ID from the field configuration and hardcode it into the workflow.
[June 23] n8n IF node (v2.2) unary operators (“true”, “false”, “empty”, “notEmpty”) require "singleValue": true inside the operator object — the n8n workflow validator will reject the node otherwise. Binary operators (equals, contains, greaterThan) must NOT include singleValue. Also: the conditions object requires "options": {"version": 2} alongside the conditions array — omitting it causes a validation error.
[June 23] n8n Webhook node with responseMode: “responseNode” requires a LINEAR chain (Webhook → Respond to Webhook → processing nodes). Connecting Webhook output to both Respond to Webhook AND a processing node in parallel triggers a validator error. The correct pattern: Respond to Webhook fires immediately (200 OK to caller), then n8n continues executing the downstream chain asynchronously. Also requires onError: “continueRegularOutput” on the Webhook node. When rewiring workflow connections, replacing the entire connections map is more reliable than removing and re-adding individual connections — especially for node names containing special characters.
[June 23] SAM.gov API v2 (api.sam.gov/opportunities/v2/search) returns results under opportunitiesData array (not data). Place-of-performance state is at placeOfPerformance.state.code. Agency hierarchy is in fullParentPathName as a dot-separated string (e.g. “DEPT OF DEFENSE.DEPT OF ARMY.CORPS”). Primary contracting officer is in pointOfContact array where type === 'primary'. Response deadline is in responseDeadLine ISO format — trim to first 10 chars for Pipedrive date field.
[June 23] n8n Code node validator flags “Cannot return primitive values directly” when a filter() callback inside runOnceForAllItems mode uses explicit return true / return false statements — the validator scans returns statically and misidentifies callback returns as top-level returns. Fix: replace filter + explicit-return dedup with a Map-based loop (dedupMap.set(key, value)) which avoids bare return statements.
[June 22] Pipedrive custom field type: “integer” is not a valid field type for deal fields or person fields — Pipedrive returns a validation error even though the UI can display whole numbers. Use “double” for any numeric field (whole or decimal). Pipedrive renders double fields as clean integers in the UI regardless.
[June 22] Pipedrive stage rename preserves the stage ID — only the display name changes. All downstream n8n workflow conditions, routing logic, and Pipedrive native automation triggers that reference a stage ID by number remain fully valid after a rename. Stage IDs only change if you delete and recreate the stage, so renames are always safe without touching any workflow logic.
[June 22] Pipedrive Deal Link custom field (28acc196575fb788fca703799c49a6280920bb38) is a shared field across all 4 entity pipelines (VC, AV, AR, AC) — the same field key reads and writes on any pipeline’s deal. [June 24] Pipedrive notes API — pinned_to_deal_flag: 1 in the POST /v1/notes body pins the note to the deal record for immediate visibility when opening the deal in Pipedrive. Without this flag, the note is written to the activity feed only and does not surface prominently in the deal view — critical for workflow-generated drafts that require immediate review before action.
[June 25] USAspending.gov (/api/v2/search/spending_by_award/) filters on action_date (obligation/modification date) by default — not period-of-performance end date. To target contracts expiring in a future window, use a broad 5-year past action_date range to capture all active multi-year contracts, then apply client-side POP end date filtering in a Code node. USAspending is fully free and keyless — POST with JSON body only. NAICS filtering via naics_codes array in the filters object. Award type codes A, B, C, D = definitive contracts (excludes IDIQs, delivery orders, grants). The validator does not catch this at build time. Always set Code nodes that reference .first() to runOnceForAllItems.
